# Operational Workflow

## Create and track records

Users create Technical Assistance records at `/assistance` or Other Task records at `/tasks`. Required fields include the activity date, shift, the type-specific subject/details, start time, assignee and accountable person. Accountable Person defaults to the signed-in user; USERs see their own display name as read-only on create and edit, and the server enforces that name on every create/update regardless of payload. ADMINs retain the dropdown, default to their own name on create, and may select any user. Technical Assistance has Problem followed by optional Cause, Resolution and Remarks fields; Other Tasks are unchanged. Both forms provide searchable Shift; Technical Assistance also has searchable Location, Show / Group and Category, while Other Tasks has searchable Activity Type only. Other Task forms, lists and details do not show or edit Location or Show / Group, and task APIs ignore both fields. Existing task Location and Show / Group values remain stored. Authenticated users can add a value with each field's adjacent plus button; this creates or restores an active, audited MasterData entry, adds it to the dropdown immediately and selects it. Show / Group is optional for Technical Assistance. Remarks are optional. The server validates record data and creates an owner link to the signed-in account.

The Technical Assistance Client / Problem column summarizes the client, Problem, Cause, and latest Resolution and Remark work logs, falling back independently to legacy Resolution and Remarks fields when no typed log exists. The Other Tasks Description column shows the description and latest Remark work log, falling back to legacy Remarks when no typed log exists. If neither typed summary is available, the latest work log is shown as Update; with no available work log, the list shows “Update: No updates yet.” Location and Show / Group appear only for Technical Assistance.

The Technical Assistance list columns are ID, Date / Shift, Category, Location / Show, Client / Problem, Priority, Status, Duration, Assigned To and Accountable Person. Category, Priority and Status display as separate badges and sort independently. Date / Shift shows a formatted date above the shift; Location / Show shows the location above the show. The Client / Problem column remains the widest and summarizes the client, problem, latest Resolution and Remark. Other Tasks columns are ID, Date / Shift, Activity Type, Description, Priority, Status, Duration, Assigned To and Accountable Person. Activity Type, Priority and Status display as separate sortable badges, and Description has the highest width priority. Both lists show elapsed time above the start-to-end time range for Close Pending and Closed records, including dates for cross-midnight records; Open records show elapsed time without an end time range. Technical Assistance also has a Category filter; Other Tasks filters are unchanged.

Both record lists provide Today, Yesterday, This Week, This Month, This Year, All Records and Custom periods using the Dashboard's UTC date boundaries. From and To inputs appear only for Custom. The USER filter defaults to the signed-in account; this My Records scope includes records the account owns, is currently assigned to, or has participated in by authoring an Investigation, Resolution or Remark work log. Participants retain view access after reassignment. For USER accounts, selecting All Users allows browsing records owned by any USER account and excludes records owned by ADMIN accounts. Administrators continue to view all records. Export Current View downloads the selected record type using the list's current period, user, status, shift, search, and Technical Assistance location/category filters. Administrators can export all filtered records with All Users or narrow the export to a selected user's visible records; USER exports remain limited to records available through the list's visibility rules. The grids show Assigned To from the record's `assigned` field and Accountable Person from its `accountable` field; ownership remains a separate record property.

Open records show only live elapsed duration in the list, and Started beside Elapsed Time on the detail page, refreshed every second; neither view shows an end time for Open records. Close Pending and Closed records retain their start-to-end range and final calculated duration. Reports and exports are unaffected.

On a Technical Assistance or Other Task detail page, Generate Report opens a PDF preview containing the record header and information, a Work Summary with Started, Ended and Duration, non-empty issue details, grouped Investigation / Resolution / Remarks entries, chronological activity and ownership. Empty fields are omitted. Users who can view the record can print or download the `TA-YYYY-NNNNN.pdf` or `OT-YYYY-NNNNN.pdf` report, or email it to the recipients configured in their Email Reports profile using the saved Gmail sender settings. The email is a notification containing only the reference, status, applicable location/client, assignee, duration, attachment name and generated footer; incident details remain in the PDF attachment. A persistent success dialog shows the filename, recipients and send time until closed. This detail-page action does not change the Reports page, report filters or participation calculations.

The server allocates references such as `TA-2026-00001` and `OT-2026-00001` using a transactionally updated counter. The reference year comes from the server's current year.

The Dashboard and Technical Assistance / Other Tasks lists receive live invalidation events when records or work logs change. They refresh through their existing APIs, preserving the current user, filters and list state; reconnecting clients refresh to catch changes missed while offline. Reports, report calculations, email previews and email sending are not part of this live-refresh behavior.

## Status lifecycle

Allowed transitions for the single-record update endpoint:

```text
OPEN -> CLOSE_PENDING -> CLOSED
			|               |
			+----> OPEN <----+
```

Open records persist null end date and end time across create, update, batch and import saves; existing Open rows are normalized by migration. The create and edit forms keep both fields visible and clear them when Open is selected; the detail page shows elapsed time and never shows a completed Ended/Duration pair for Open records. The Quick Actions transition to Close Pending supplies the browser-local current end date/time when values are absent, matching the local wall-time format of record start times. Close Pending and Closed records require both end values. A direct transition from Open to Closed is rejected by the single-record endpoint; the record must first enter Close Pending. Batch status edits use a separate update path and do not enforce the same transition or full-record validation rules. Reporting logic is unchanged.

The detail view presents a single Record Timeline combining Reported, Assigned, Endorsed, status-transition and work-log events in timestamp order. One continuous accent-colored rail is drawn from the first centered event node to the last without extending below it. Each node briefly glows as the rail reaches it, and its theme-aware panel card begins fading/sliding into view at that same arrival time, paced by distance along the rail; after the sequence, only the newest node retains a subtle static glow. Reduced-motion preferences disable the animation. Cards have a clear gutter from the rail and no horizontal connectors. Small Investigation, Resolution, Remark or System Event badges identify each event; the entry form appears above the timeline. Users with record edit permission can add an Investigation, Resolution or Remark entry while a record is Open. Close Pending and Closed records retain viewable work logs but replace mutation controls with a status-specific lock message; the API rejects create, edit and delete requests for those statuses. When a record returns to Open, permitted add, edit and delete controls are available again. Administrators and record owners can edit or delete any work log; authors can edit or delete their own work logs. Editing is limited to the message; type, author and creation timestamp remain unchanged, and edited entries show their modification date/time. A record with work-log history cannot be deleted through the single-record delete endpoint.

## Ownership, assignment and locking

The account that creates a record is its owner; `assigned` and `accountable` are stored as names. For Administration imports, a unique `Accountable Person` match is also the record owner; blank, unknown, or ambiguous values fall back to the importing administrator as both owner and accountable person. `Import My Records` keeps the importer as owner and accountable person. Administrators may lock/unlock records. Locking prevents non-admin edits. Batch actions can act on multiple selected records and report records skipped for permission reasons.

## Import workflow

1. Choose an import scope: `Technical Assistance Only`, `Other Tasks Only` or `Both Worksheets` (the default), then choose a CSV or Excel file (maximum 10 MB). The same scopes are available from either record page.
2. The server maps known header aliases, including `Cause` on Technical Assistance and `Accountable Person` on both record types, normalizes dates, times, status and priority, then validates rows. Excel date/time serials are supported. `CLOSED` rows need an `End Date` and `Time Ended`; missing end fields on `CLOSE_PENDING` rows are filled with the current date and time. The downloadable workbook template includes `Cause` on Technical Assistance, `Accountable Person` and `End Date` on both record sheets.
3. Review the status banner and total, valid, warning and error counts. Compact Technical Assistance and Other Tasks summaries show how many records are ready for import, or report when a worksheet has no records. The accountability notice identifies the importer fallback; the preview also lists valid Assigned To matches and, for Administration imports, valid Accountable Person matches. Administration preview includes an expandable temporary per-row accountability diagnostic with match, warning and validation outcomes. Warnings and validation errors are listed in dedicated sections; ignored worksheets and columns are also reported. Excel imports select worksheets by their canonical names; no worksheet picker is needed.
4. Confirm import. Valid rows are inserted with newly generated references. `Import My Records` assigns ownership and accountability to the importer. Administration imports assign both to the matched Accountable Person when there is exactly one user match; blank, unknown, or ambiguous values assign both to the importing administrator. Invalid rows are skipped and returned in the result.

For Excel, the selected canonical worksheets are processed; in `Both Worksheets` mode, both named worksheets are required and records are created in their matching tables. All other worksheets, including `WorkLogs`, are ignored and reported in the preview and import response. The completion summary reports imported counts for each processed worksheet. CSV parsing supports quoted commas/newlines and remains a single-record-type import.

`Assigned To` is optional and is matched against user full names. A unique match is assigned to the record. An unknown or ambiguous name leaves the record unassigned and generates a warning without blocking import. Administration imports also match `Accountable Person` against user full names: a unique match sets both accountability and ownership to that user, while a blank value defaults both to the importing administrator. An unknown or ambiguous value generates a warning and defaults both to the importing administrator. Imports from the Technical Assistance and Other Tasks pages continue to ignore workbook accountability and set both owner and `Accountable Person` to the importing user. The importer does not accept online file links.

The Administration page presents this as `Administrative Record Import` for historical data migration, bulk record onboarding and team-wide imports. Its guidance explains workbook user matching and the administrator accountability fallback; the downloadable template is labeled for Administration imports.

Other Tasks imports do not include `Location` or `Show Group`: these are legacy database columns no longer used by the task forms or APIs, and imported values are discarded. The workbook template omits them.

## Reporting and email

Reports offer Today, Yesterday, This Week, This Month, This Year, All Records and Custom periods. From and To fields appear only for Custom. All Records omits date filtering from the report, Excel export and email while retaining activity, status, scope, user and permission filtering. Administrators can choose all records or their participation and optionally select a user; non-admin users are limited to their participation scope. Excel downloads and email attachments use the same workbook with Summary, Technical Assistance, Other Tasks, Work Logs and Timeline worksheets. Work Logs contains one row per entry with Record No, Record Type, Work Log Type, Timestamp, User and Message; Timeline contains one row per event with Record No, Timestamp, Event Type, Description and User. Both include entries belonging to records selected by the report filters. Email preview renders the report using the configured Gmail sender/recipients; sending attaches `Report.xlsx` and `Report.pdf`. The PDF is rendered from the same email HTML shown in preview, and PDF generation must complete with a non-empty buffer before the email is sent. The production Docker image supplies Chromium for this server-side rendering.

The Audit Logs page initially displays All Records and offers the same seven periods as the Dashboard. From and To appear only for Custom, and the selected period is applied to `createdAt` in the audit-log database query. Search, category and action filters are client-side and combine together. The Action choices are limited to the selected category, and changing Category resets Action to All Actions. Audit detail dialogs display Reference No for record create, update, status, endorsement, lock, unlock and delete events, along with any available Client, Show / Group, Location or Activity Type summary fields. Structured changes render in a Field / Previous / Updated table with friendly field labels; older changed-field arrays remain readable as lists. Record update, status, endorsement, lock and unlock events store actual field transitions as `changes` entries with `field`, `oldValue` and `newValue`. Delete events retain the reference number, subject, description, assignee and record type in the visible details. Record audit payloads exclude passwords, SMTP passwords, tokens and 2FA secrets. Authentication includes login/logout and 2FA actions; User Management includes profile/user updates and `USER_CREATED`, `USER_DELETED`, `USER_DEACTIVATED` and `USER_ROLE_CHANGED`; Administration includes master-data actions; Reports includes report-email actions; Technical Assistance and Other Tasks each include record create/update/delete/import/lock/unlock actions; System includes combined imports. Excel export accepts the selected category alongside its existing search, action and custom From/To filters.

## Sign-in verification

Users can enable Email Two-Factor Authentication from Account Settings. A code is sent to the email address saved in the profile, and 2FA is enabled only after the six-digit code is verified. Email delivery uses that user's saved Gmail sender and app password; both must be configured before enabling. Login validates the password first, then requires a one-time code before NextAuth creates a session. Codes are single-use, expire after 10 minutes, and newly issued codes invalidate older unused codes. Code issuance is limited to five per user in a rolling 15-minute window. The initial login challenge bypasses the 60-second resend cooldown; explicit resends are subject to it. Users can disable 2FA in their own profile, and administrators can disable it from User Management for account recovery. The enable, disable, delivery, success and failure events are available in Audit Logs.

At sign-in, the login page shows Credentials and Verification steps. A credential submission makes one initial code request and ignores duplicate submissions while that request is in flight. When 2FA is required, entering all six digits submits the code automatically; invalid codes clear the inputs and return focus to the first digit. Explicit resend is disabled during the cooldown; the remaining seconds or a server-provided retry delay are displayed below the OTP inputs. Browser and server logs include a request ID and request type to correlate requests. Verification emails display the code, expiry and security guidance in responsive HTML and plaintext formats. Account Settings show the user's role, active status, 2FA state and last login; Email Reports configuration is collapsed by default.

Credential and verification submissions show staged progress at 35%, 75% and 100%, with a success state held for one second. After successful sign-in, a full-screen transition view displays “Login Successful” and “Security Verification Complete” above a checklist. “Identity Verified,” “Secure Session Established” and “Workspace Loaded” complete one at a time at 800 ms intervals, then the page redirects to the dashboard. These visual states do not change authentication or session creation behavior and respect reduced-motion preferences.

## Backup and restore

Administrators can download a versioned JSON backup. Restore supports Merge and Replace and provides a count preview before applying the operation. Merge skips existing users/records/master-data/audit rows according to their identifiers and updates branding; Replace clears database tables before restoring. Restore also resets PostgreSQL ID sequences and applies reference counters from the file. Uploaded files are not in the JSON backup; work logs are also not currently included.
